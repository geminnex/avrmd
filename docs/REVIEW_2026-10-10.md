# AVRMD Full Review — 2026-10-10

A full review of features, architecture, security and fit with the north star, done before
planning the next stretch. Three reviewers worked in parallel: Sentry (security), Archer
(architecture) and Atlas (product and features). Avier then verified every important
finding against the code and the live site; anything not verified is marked as such.

## Verdict

**The foundations are sound; the site is not finished, and in a few places it promises
more than it does.**

- There are no critical or high security issues: no auth bypass, no IDOR, no SQL
  injection, no stored XSS. There are six medium issues, all fixable in a few days.
- The core loop (profile → routed question → answer → notification) and the AI
  assistant work. Nobody uses them yet: 1 account, 0 profiles, 0 questions.
- The largest risks are in **trust and operations**, not code:
  - Four forms discard what people type.
  - There are no database backups.
  - Deploys rebuild the live directory in place.
  - Several pages and docs describe a site that does not exist.
- Against the goal ("not too complex, AI first, don't make people fish in an ocean"),
  the site is **too broad for its content**: 31 pages, about 29 menu links, and 54
  catalog records.

## 2. Security (Sentry, verified)

0 critical · 0 high · 6 medium · 8 low · 5 info.

| # | Finding | Evidence | Fix |
|---|---|---|---|
| M1 | No security headers (CSP, HSTS, frame-ancestors, nosniff, Referrer-Policy) | `next.config.ts`; live `curl -sI` sends none | Add headers in `next.config.ts` |
| M2 | The media bucket can be listed anonymously; keys expose uploader user ids | `GET /media/avrmd/` returns 200 with an XML listing (verified: 3 objects) | Make the bucket policy GetObject-only; stop key paths from carrying user ids |
| M3 | The public handle is derived from the email local part before the email is verified | `lib/db/repositories/users.ts:58-67` | Use a neutral generated handle; reserve system words |
| M4 | Post media accepts any URL and renders it as `<img>` for all viewers (tracking pixel) | `app/api/posts/route.ts:27-30`, `components/post-card.tsx:63` | Accept only URLs of the member's own uploads |
| M5 | Rate limits are in-memory, per process, keyed on `x-forwarded-for`; several routes have none; one actor can exhaust the assistant's daily model budget | `lib/rate-limit.ts` plus 4 copies; `app/api/assist/route.ts` | One DB-backed limiter; per-visitor assistant quota under the global cap |
| M6 | The magic link is consumed by a GET; consumption is select-then-update (racy); login CSRF is possible | `app/api/auth/verify/route.ts`, `verification-tokens.ts:24-41` | Confirm-page POST; atomic `UPDATE … RETURNING` |
| L1 | A malformed id returns HTTP 500 | live `GET /api/posts/not-a-uuid/comments` → 500 (verified) | Validate ids → 404 |
| L2–L8 | Email bombing via sign-in requests; sign-out CSRF; residual prompt-injection wording; unauthenticated DB-heavy endpoints with no limit; unmoderated talk submissions; no upload quota and orphaned files; handle impersonation | see `security.md` | Covered by Phase A/B tasks |

**Outside AVRMD but on the same host:** `/home/openclaw/Caddyfile` is world-readable and
contains a plaintext shared password for other cyalin.com sites.

**Verified as correct:**
- Magic-link tokens are 32 random bytes, stored only as hashes, expire in 15 minutes and
  are single use (apart from the M6 race).
- Session cookie flags are correct.
- There is no open redirect.
- Sign-in responses do not reveal whether an account exists.
- Group posting and accept-answer check authority on the server.
- There is no `dangerouslySetInnerHTML`.
- Uploads are checked by magic bytes, and SVG is refused.
- The server never fetches a user-supplied URL.
- Assistant citations and actions are validated, so the model cannot produce a clickable link.
- No secrets are in git or its history.

## 3. Architecture (Archer, verified)

**Sound, and worth keeping:**
- Pages degrade honestly when the database or the model is down.
- Catalog, topic, stage and problem pages stay static, with auth in client islands.
- The trust model is enforced in code: signals carry no review state, candidates need
  explicit approval, the schema is test-enforced, and the assistant's output is validated.

| Severity | Issue | Consequence |
|---|---|---|
| High | Deploys rebuild `.next` in the live directory while the server runs; no release dirs, health check or rollback | Requests can hit missing chunks during a build; a bad build has no way back |
| High | **No backups**: Postgres has none; `candidates.json`, `seen.json` and `signals.json` are gitignored single copies (verified: no AVRMD backup timer, while two other apps on the host have one) | One disk or container failure loses every account, question and the review queue |
| High | 10 of the schema's tables are used by no code (`entity_relations`, `source_records`, `field_provenance`, `content_revisions`, `catalog_submissions`, `ownership_claims`, `private_inquiries`, `moderation_reports`, `audit_events`, `ai_suggestions`); `ARCHITECTURE.md` presents them as the core domain | The docs describe a different system; dead weight |
| High | The catalog is a JSON file bundled at build; every approval needs a rebuild and restart; lookups are linear; the promised Postgres full-text search does not exist | It does not scale from 54 to thousands of records |
| Medium | A dead Cloudflare/OpenNext `postbuild` path; `output: "standalone"` conflicts with `next start` (warning on every start, verified) | Confusing builds; a possible build failure |
| Medium | The robot writes non-atomically into the git tree; `fda-xr-devices.json` (tracked) changes daily; the timer has no failure alert | Torn reads fall back to empty silently; a failed robot goes unnoticed |
| Medium | Almost no logging; many silent `catch` blocks; no `error.tsx`; `/posts/[id]`, `/members/[handle]` and `/network` lack DB-down handling; `/network` makes one query per post | Problems are invisible until a user hits them |
| Medium | The home page is `force-dynamic` only to shuffle three talks | Every visit hits the DB; nothing can be cached |
| Medium | Env precedence is opaque (`/etc/avrmd.env` silently overrides the project files) and there is no startup validation | Already caused two silent misconfigurations (SMTP, then the AI key) |
| Medium | The assistant rebuilds its corpus and loads all questions and profiles on every request | Fine at about 650 documents; linear CPU as content grows |
| Low | 5 copies of `timeAgo`, 5 rate limiters, 2 query-string builders; `latest` pins on 9 dependencies; no tests for API routes, auth, repositories or uploads | Drift; unreviewed upgrades |

## 4. Fit with the north star (Atlas, verified)

**What each audience can do today, and its biggest gap:**

| Role | Can do today | Biggest gap |
|---|---|---|
| Clinician | Browse topics, solutions and talks; ask the AI; post a routed question | Nobody to answer yet; no adoption guides (procurement, IRB, reimbursement); a thin catalog |
| Researcher | 400 signals, talks | Only 2 evidence records; no collaborator search; signals are unreviewed |
| Engineer / developer | 7 technical problems, stage guides, talks | Few problem pages; no SDK, dataset or OpenXR resources; no route to clinical partners |
| Device supplier / manufacturer | Read; 120 FDA devices are listed | **Claim and promotion forms discard input.** This is the fastest audience for both content and revenue, and it is fully blocked |
| Business / investor | Signals, 14 organizations | No market map and no digest; opportunities are empty |

**Simplicity.** The site is too complex for its content. The owner's direction ("not
complex, assistant first, bring in links and features when needed") is half
implemented: the assistant now answers with sources and next steps, but it is still a
floating button beside 15 destinations rather than the front door.

**Trust: places where the site promises more than it does:**
- `/about` → "What is live today" is wrong in both directions.
- Four forms discard input, and their calls to action repeat on the home page and in the footer.
- `/for-organizations` and `/participate` describe review queues and replies that do not exist.
- `/opportunities` says listings are "posted by the organisations behind them"; no one can post.
- The north star's "largest and most complete" must not appear publicly until the numbers support it.

**Cold start.** The empty member directory and the empty question list in the main
navigation make the site look abandoned. Question routing currently reaches nobody.

**Missing from the plan entirely:**
- Onboarding
- Email notifications and digests
- Moderation tools
- Analytics
- SEO (`robots.txt` and `sitemap.xml` both 404, verified)
- A web review UI and claim verification
- A privacy policy, terms of use, account deletion and copyright takedown (required by `TRUST_SAFETY_IP.md` before launch; none exist)
- An evaluation set for the assistant
- Partnerships

## 5. Corrections to earlier statements

- Atlas reported "no production SMTP". That is wrong: Purelymail is configured and verified.
- "4 FDA devices" counts catalog records; `/clearances` lists all 120.
- The live assistant currently runs retrieval-only because `/etc/avrmd.env` sets an empty
  `OPENROUTER_API_KEY` and `OPENROUTER_MODEL=openrouter/free`. Those override the
  project file, the same failure as SMTP earlier. Removing the two lines fixes it.

## 6. What changes in the plan

The phases continue the existing roadmap's numbering (Phases 0–4 are done), so earlier
docs and commits stay valid. See [`IMPLEMENTATION_ROADMAP.md`](IMPLEMENTATION_ROADMAP.md)
for the full plan:

| Phase | Name | What it covers |
|---|---|---|
| 5 | Trust and safety | Fix or remove everything that promises more than it does; close the security mediums; add legal pages and backups |
| 6 | Operations | Safe deploys, alerts, logging, one rate limiter, env validation |
| 7 | Simplify, assistant first | Ask-first home page; navigation cut to five items; dead surfaces removed |
| 8 | Content engine | AI triage of the review queue with a web approval screen; catalog grows; move it to Postgres when it does |
| 9 | Return loop | Onboarding, email notifications and a weekly digest, moderation basics |
| 10 | Seed the community | Founder-led: invite the first 20–50 experts; editors answer publicly |
| 11 | Live sessions, projects, events | The old Phase 5 and 6, now after there are people to use them |

The old Phases 5 (live sessions) and 6 (projects) move to Phase 11: both need members,
and members need the earlier phases.
